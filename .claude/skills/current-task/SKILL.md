# 执行当前任务

把 `docs/tasks/current.md` 视为唯一任务队列和会话交接来源。一次调用最多处理一个任务；该任务完成或受阻后立即停止。

## 解释用户意图

- 无参数、`实现`、“实现当前任务”或“继续下一步”：若存在进行中任务则恢复；否则启动第一项已承诺待办。
- `继续` 或“继续当前任务”：只恢复进行中任务；不存在时停止，不启动待办。
- `开始下一任务`：仅在没有进行中任务时启动第一项已承诺待办；存在进行中任务时停止并报告状态冲突。
- `验收` 或“验收当前任务”：对进行中任务执行完成标准；不得借验收新增计划外行为。若没有进行中任务，停止并说明。
- 无论哪种意图，都不得从 `backlog.md`、最近完成记录或未承诺的 Feature Spec 中自行选择任务。

## 1. 建立最小上下文

1. 项目根目录的 `CLAUDE.md` 已导入 `AGENTS.md`，不要为了确认规则再次完整读取它们。
2. 读取 `docs/tasks/current.md`，只确定任务状态、目标任务及其引用。
3. 运行 `git status --short`；需要判断已有改动时，先用 `git diff --stat` 或 `git diff --name-only`，再按文件查看局部 diff。
4. 只读取目标任务引用的 Feature Spec，以及任务范围实际需要的 `README.md`、`PRODUCT.md`、`ARCHITECTURE.md`、`DECISIONS.md` 局部内容。先搜索标题或符号，不预读所有项目文档。
5. 若工作区已有改动，先区分哪些是用户或前序会话留下的内容；保留并避开无关改动，不覆盖、不回滚。

## 2. 选择唯一任务

按照用户意图选择任务后，检查：

1. 最多只有一个任务处于“进行中”。
2. 目标任务有明确目标、范围、非范围、依赖和完成标准。
3. 所有依赖已经满足，Feature Spec 不存在阻止实现的开放问题。
4. 任务颗粒度符合 `AGENTS.md`，能在一次聚焦会话中独立实现、验证和交接。

如果存在多个进行中任务、依赖未满足、规格冲突、关键需求缺失或任务仍需拆分：可以修正纯任务文档中的明显状态问题，但不得猜测产品需求或开始实现；报告阻塞后停止。

## 3. 执行状态门禁

- 恢复进行中任务：根据“当前进度”、工作区差异和验证记录确认真实完成边界，不重复已完成工作。
- 启动待办任务：在修改任何实现代码、实现性测试、构建配置或功能产物前，先把目标任务改为“进行中”，填写开始日期和真实当前进度并保存。
- 验收任务：目标必须已经处于“进行中”，保持原范围，只处理达到现有完成标准所必需的问题。

状态门禁未完成前不得开始编码，也不得先实现后补记状态。

## 4. 压缩前检查点与压缩后恢复

### 写入检查点

在以下任一时机，先把真实状态写入目标任务的“当前进度”，再继续：

- 完成一个主要实现阶段；
- 即将运行完整测试、完整构建、release 或真实应用验证；
- 准备主动执行 `/compact`；
- 上下文接近自动压缩阈值；
- 错误或新证据导致下一步实现路径发生变化；
- 准备暂停、退出或把同一任务交给下一会话。

“当前进度”保持简短，只记录：

```markdown
- **当前进度**：
  - **已完成**：已经落盘且无需重复的结果。
  - **剩余**：仍属于本任务但尚未完成的内容。
  - **修改文件**：本次相关文件；标明需要避开的用户已有改动。
  - **已验证**：实际运行的定向验证及结果；完整命令留到验证记录或交接。
  - **下一动作**：恢复后唯一应先执行的动作。
```

检查点不改变任务状态，不写流水账、完整日志或可直接从 Git 恢复的普通实现细节。内容已经变化时才更新，避免每次工具调用都改文档。

### 压缩后恢复

若会话显示已经压缩、上下文主要来自摘要，或关键完成边界无法确认，在继续修改前执行：

1. 重新读取 `docs/tasks/current.md` 中目标任务的状态、当前进度和完成标准。
2. 运行 `git status --short`，再按需使用 `git diff --stat`、`git diff --name-only` 和相关文件的局部 diff。
3. 对照磁盘事实核对“已完成”“剩余”“修改文件”“已验证”和“下一动作”；磁盘与 Git 优先于摘要。
4. 确认仍只有一个进行中任务，目标、依赖和范围没有被摘要改变。
5. 从记录的唯一下一动作继续；不重复已经完成的实现、搜索、昂贵测试或完整构建。

若无法区分用户已有改动、摘要与磁盘明显冲突，或恢复需要猜测产品需求，先更新真实阻塞并停止，等待 Codex 或用户确认。

## 5. 实现

1. 严格按目标任务的范围和非范围交付最小完整垂直切片。
2. 不静默增加需求、重构无关代码、引入不必要依赖或修改后续任务。
3. 文档与代码冲突时停止扩大实现，说明冲突、影响和需要 Codex 或用户决定的事项。
4. 使用搜索、符号和行范围定位代码；遵守 `CLAUDE.md` 的工具输出预算，不把完整文件、大型 diff 或正常构建日志倾倒进上下文。
5. 每完成一个可验证阶段就检查实际差异，及时修正偏离范围的问题。

## 6. 验证与收尾

1. 先运行与修改直接相关的定向测试，再运行任务“完成标准”明确要求的完整测试、构建、格式化、静态检查或人工验证。
2. 大型输出写入 `/private/tmp` 下的任务专用日志；保存真实退出码，成功只读取摘要，失败只读取相关错误和必要上下文。
3. 只把实际运行过且通过的验证记录为通过。因环境或权限未运行的检查必须明确标记为未运行。
4. 所有完成标准满足后，更新 `docs/tasks/current.md`：记录结果和验证事实，把任务改为“已完成”，并按项目规则维护最近完成数量。
5. 若验证失败且能在任务范围内修复，修复后复验；若需要扩大需求、修改架构决策、依赖外部确认或无法安全继续，保持真实状态并写明当前进度和阻塞。

## 7. 停止与交接

完成或受阻后立即停止，不自动开始下一任务。最终只报告：

- 本次处理的任务及最终状态；
- 实际完成的行为和主要变更文件；
- 实际执行的验证及结果；
- 尚未完成、阻塞或需要用户确认的事项；
- 下一次可使用的入口，例如 `/current-task` 或先回到 Codex 做规划。

不要粘贴完整正常日志，不建议在同一调用中顺手处理下一项待办。
