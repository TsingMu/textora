# Markdown fenced code block 通用格式化

> 状态：草案

## 背景与目标

Textora 已能在 Markdown 源码视图中显式格式化光标所在的闭合 `json` fenced code block，但入口固定为 `Format JSON`，其他常见代码块仍需复制到外部工具处理。

本功能拟把入口统一为 `Format`：用户点击后，应用根据当前闭合 fenced code block 的语言标记选择本地格式化器，并且只修改该代码块。具体语言别名、格式化风格、依赖方案和分阶段交付边界需在规格确认任务中决定。

## 候选范围

- 将 Markdown 源码工具栏的 `Format JSON` 改为通用 `Format`。
- 根据光标所在闭合 fenced code block 的 info string 首个 token 选择格式化器。
- 首期候选语言为 JSON、JavaScript、TypeScript、YAML、SQL、Java、Python 与 Shell。
- 每次只格式化光标所在代码块，以单次 CodeMirror 事务提交，并可由一次撤销恢复。
- 无法识别语言、语言未支持、代码块未闭合或内容无效时，显示明确的非阻塞原因且不修改源码。
- 所有格式化均在应用本地完成，不增加网络、远程执行、shell 执行或宽泛文件权限。

## 延续的安全边界

- Markdown 源码仍是唯一权威数据源；opening fence、closing fence、文档其他内容、编码与换行保存契约不得被格式化器改写。
- 只在用户显式点击时格式化；不在输入、粘贴或保存时自动运行。
- Preview 左侧源码沿用同一入口；WYSIWYG 不执行 fenced code block 格式化。
- 只读、加载、保存、冲突处理、关闭确认与另存为面板期间继续沿用现有交互锁定。
- 格式化失败不得产生部分编辑、脏状态变化或新的撤销历史。

## 非范围

- 批量格式化多个代码块、整个 Markdown 文档或普通源码文件。
- WYSIWYG 代码块格式化、选区局部格式化、保存时格式化或自定义格式化配置。
- LSP、诊断、代码执行、外部进程、云端格式化服务或项目级工具链探测。
- 在本规格未确认前承诺某个第三方格式化库、输出风格或全部候选语言一次性交付。

## 待确认的用户流程

1. 用户把光标放入闭合 fenced code block 的内容区。
2. 用户点击 Markdown 源码工具栏的 `Format`。
3. 应用规范化语言标记并选择本地格式化器。
4. 成功时只替换该代码块内容并保留有效光标位置；失败时提示原因且源码不变。
5. 用户可用一次撤销恢复格式化前的完整代码块内容。

## 初步验收方向

- [ ] 现有严格 JSON 格式化行为迁移到通用入口后不回退。
- [ ] 每个最终纳入首期的语言及其别名、有效输入、无效输入和确定性输出均有自动化覆盖。
- [ ] 未知/未支持语言、未闭合代码块、fence 行与块外光标均不修改文档，并给出可区分原因。
- [ ] 格式化只修改当前代码块，保持其他代码块、fence 与 Markdown 内容不变，并可一次撤销。
- [ ] Preview、WYSIWYG、只读、忙碌、多标签、保存及关闭保护边界不回退。
- [ ] 新依赖经过体积、许可证、macOS WebKit 兼容性和纯本地运行评估。

## 依赖与约束

- 依赖已完成的 `docs/features/markdown-fenced-code-editing.md`、Markdown Preview、多标签会话、保存与关闭保护。
- 复用现有 fence 上下文识别与 CodeMirror 事务链路，不绕过 `onChange`、脏状态或撤销历史。
- 遵守 `docs/ARCHITECTURE.md` 的源码权威、格式能力可退化与最小权限不变量，以及 D-004、D-007。

## 开放问题

- 各语言接受哪些 fence 标记及别名，大小写和常见变体如何规范化？
- JavaScript、TypeScript、YAML、SQL、Java、Python 与 Shell 分别采用哪个可在 macOS WebKit 中纯本地运行的格式化器？是否需要拆分首期语言集合？
- 各格式化器采用何种固定风格；是否能在不引入用户配置的前提下保持结果稳定、可预测？
- 如何隔离解析器异常、超大代码块耗时与第三方库错误，确保失败时零修改且不阻塞基础编辑？
- 新依赖对 bundle 体积、许可证、构建时间和维护面的影响是否与真实自用收益匹配？
- 实现任务应按共享格式化契约、格式化器引擎或单语言垂直切片如何拆分，才能保证每项可独立验收？
