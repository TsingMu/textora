## D-004：采用 Tauri、React、CodeMirror 与 Rust

- **状态**：已接受
- **日期**：2026-07-14
- **背景**：产品需要成熟文本编辑体验、Markdown/Mermaid Web 生态和可靠的本地文件安全边界，并希望避免为应用捆绑完整浏览器。最初选择时还考虑了 D-003 的跨平台范围；该范围后由 D-007 取代，但技术栈继续适合 macOS 产品。
- **决策**：使用 Tauri 2 作为桌面壳，React + TypeScript + Vite 构建界面，CodeMirror 6 作为编辑器，Rust 负责文件与编码安全边界。
- **影响**：产品只要求验证 macOS WebKit 行为；文件系统通过受限 Tauri 命令暴露，前端不获得宽泛权限。Tauri 和 Rust 依赖可以保留其可移植性，但 Windows 构建与 WebView2 行为不再是产品验收条件。

## D-005：首版文件规模与编码边界

- **状态**：已接受
- **日期**：2026-07-14
- **背景**：基础编辑必须先明确可验证的文件规模与无损编码规则。
- **决策**：首版支持最大 50 MiB 的 UTF-8、UTF-8 BOM 与严格 GBK/Windows CP936 文件。拒绝 GB18030 四字节序列和无法无损识别的编码。GBK 无法表示编辑内容时阻止保存并提供另存为 UTF-8。
- **影响**：Rust 文档核心负责无替换解码/编码、换行元数据、冲突检测和原子保存；不得静默改变编码或插入替代字符。

## D-006：GBK/UTF-8 编码歧义时保持编码与内容无损

- **状态**：已接受
- **日期**：2026-07-21
- **背景**：检测顺序为 UTF-8 优先（D-005、基础文本编辑规格）。部分 GBK 字节序列也构成合法 UTF-8：有些会解码成不同字符（如「一」的 GBK 字节 `D2 BB` 会被读成 U+04BB），纯 ASCII 与空内容则保持文本但会被识别为 UTF-8。若允许按 GBK 普通保存，重新打开可能静默改变内容或丢失 GBK 编码身份。
- **决策**：只有 GBK 编码后的字节经本工程打开流程仍被识别为 GBK、且还原成与原内容相同的字符串时，才允许 GBK 普通保存；否则核心以独立错误 `EncodingAmbiguous` 阻止保存，并提示另存为 UTF-8。纯 ASCII 与空内容虽不会改变文本，但会被 UTF-8 优先流程识别为 UTF-8，无法保持 GBK 编码身份，因此显式以 GBK 保存时同样拒绝；原本就是 ASCII 的文件会在打开时归为 UTF-8，不受影响。
- **影响**：这是对 D-005「GBK 无法表示时阻止保存」之外、面向重开无损性的安全限制；不改变 UTF-8/UTF-8 BOM 保存。未来若引入可靠的带外编码提示（会话层持久化目标编码并传给打开流程），可放宽此限制；在该机制落地前，核心不得静默写出无法按原编码和内容重开的 GBK 文件。

## D-007：macOS 个人文本工作台与 Windows 文本生态兼容

- **状态**：已接受
- **日期**：2026-07-27
- **背景**：项目来源于用户在 Windows 内网工作中需要分别使用 Notepad++、Typora 与 UltraEdit 完成普通文本、Markdown 和列块编辑，希望在 macOS 自用时把这些高频工作流整合到一个应用。实际需求不是在 Windows 上替代这些现有工具，也不是开发面向公开市场的跨平台通用编辑器。
- **决策**：Textora 只将 macOS 13+（arm64/x86_64）作为产品运行与验收平台。产品兼容 Windows 与 Unix 来源文本的 UTF-8、UTF-8 BOM、严格 GBK/CP936、LF、CRLF 和 Mixed 格式，并逐步提供列块编辑、Markdown 分栏与所见即所得等真实自用工作流。Windows 来源文件兼容不等于提供 Windows 应用；Windows 构建、WebView2 行为和 Windows 原生对话框不再是功能完成条件。
- **影响**：现有 Tauri、React、CodeMirror 与 Rust 技术栈继续使用；已经完成的 Windows 可移植性设计和相关测试无需删除，但不再产生待验证平台债务。产品优先级按真实自用价值排序，不以公开分发、商业化、外部用户增长或通用编辑器功能数量为目标。新规格和验收只要求 macOS 运行行为，同时继续对 Windows/Unix 来源文件执行确定性的字节、编码和换行验证。
